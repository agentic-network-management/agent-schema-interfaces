         Schema Interfaces for Network Management Agent Skills
               draft-huang-agent-schema-interfaces-latest

Abstract

   Network management agents can use an Agent-to-Agent protocol to
   discover peers, delegate work, observe task state, receive results,
   and cancel work.  The protocol alone does not define the application
   schemas used by an analysis agent, incident-analysis agent,
   configuration agent, or other independently developed network
   management agent.

   This document standardizes three components for the machine-readable
   schema interfaces of network management agent skills: a Schema
   Reference structure for identifying, verifying, and resolving
   schemas; a Skill Interface Schema and conforming per-skill Skill
   Interface Document; and a Skill Interface advertisement and retrieval
   procedure using describe_skill.  The Skill Interface combines the
   input, output, and supporting-record schemas defined by the agent's
   vendor or domain owner with common interaction and authority
   declarations.

   Schema identity is portable, while schema resolution is deployment-
   specific.  Schemas may be returned inline, served by the agent,
   installed as an offline bundle, or resolved through an optional
   customer-operated schema registry.  The design does not require a
   public registry or make a registry a runtime dependency for every
   task.

1.  Introduction

   Agent-to-Agent task exchange requires agreement at two different
   layers:

   1.  a protocol for agent discovery, task identity, lifecycle,
       streaming, polling, cancellation, and result transport; and

   2.  application schemas that define the meaning of the skill input,
       output, deliverables, and supporting records.

   The Agent2Agent (A2A) protocol [A2A] defines agent discovery, message
   transport, task lifecycle, streaming, polling, cancellation, and
   artifact delivery.  It does not define the domain-specific input,
   output, or supporting-record schemas used by individual skills, nor a
   common interface for retrieving and validating those schemas.  This
   document addresses that application-schema gap while leaving A2A task
   and transport semantics unchanged.

   Agent discovery and the schema-interface procedure are distinct.
   Agent discovery determines which agent to contact and how to reach
   it.  The schema-interface procedure defined in this document occurs
   after an agent has been identified and provides the machine-readable
   interface for invoking one of its advertised skills.  This document
   does not define how agents are found, selected, ranked, or matched to
   user intent.

   A common protocol envelope can deliver a JSON object without making
   that object semantically interoperable.  If the original input and an
   upstream agent's result are opaque text or unconstrained JSON, a
   downstream agent must infer their meaning.  Such inference may be
   useful for human-oriented content, but it is not an adequate
   substitute for a declared interface when agents make operational
   decisions or generate network changes.

   The three standardized components define a framework in which:

   *  common Schema Reference and Skill Interface structures are
      standardized without standardizing every domain payload;

   *  each skill declares versioned input, output, and supporting-record
      schemas;

   *  vendors and domain owners define the schemas specific to their
      agents;

   *  an agent assembles and validates a Skill Interface Document from
      the common structure and its domain schemas before advertising
      that document;

   *  a client agent retrieves and validates the selected Skill
      Interface before delegation;

   *  schemas can be resolved without assuming a particular registry
      product; and

   *  skill outputs and their supporting records can be validated before
      they are consumed or acted upon.

   The framework is intended to support independently developed agents
   from different network-management domains without forcing their
   domain payloads into one universal schema.

3.  Scope

   This document standardizes:

   *  a common Schema Reference structure for identifying, verifying,
      and resolving schemas;

   *  a Skill Interface Schema and a conforming per-skill Skill
      Interface Document; and

   *  a Skill Interface advertisement and retrieval procedure using
      describe_skill.

   In support of those three components, this document also defines:

   *  the relationship among skill inputs, skill outputs, and supporting
      records;

   *  schema identity, integrity, versioning, and resolution behavior;

   *  the relationship between these interfaces and Agent-to-Agent task
      state; and

   *  requirements for validation, caching, trust, and failure handling.

   This document does not define:

   *  the internal algorithm used by an agent;

   *  a universal schema for every network-management domain;

   *  a required schema-registry product or API;

   *  a globally centralized schema service;

   *  agent hosting, process lifecycle, or platform onboarding;

   *  authorization merely by successful schema validation; or

   *  the semantics of vendor-specific analysis, incident, or
      configuration data.

4.  Standardized Components

4.1.  Schema Reference Structure

   The Schema Reference is a common structure for identifying a schema
   by stable URI and version, declaring its schema dialect, verifying
   its content by digest, and providing deployment-specific resolution
   information.  The same structure is used for input, output, and
   supporting-record schemas.  The structure is standardized so that a
   client can identify, retrieve, and verify every schema in a Skill
   Interface without agent-specific or registry-specific interpretation.
   The referenced domain schemas and the deployment's choice of
   resolution mechanism are not standardized by the Schema Reference
   structure.

   A standardized Schema Reference also enables composition across
   independently developed agents.  An orchestrating system or
   delegating agent can compare the Schema Reference of an upstream
   output payload with the Schema Reference accepted for a downstream
   input without interpreting either schema's domain semantics.
   Matching schema identity, version, dialect, and digest provides a
   deterministic basis for deciding whether direct composition is
   permitted.

4.2.  Skill Interface

   The Skill Interface Schema defines the common structure of a Skill
   Interface Document.  A conforming document describes one version of
   one skill and binds the domain-specific input, output, and
   supporting-record schemas used by that skill to common interaction
   and authority declarations.

4.3.  Skill Interface Advertisement and Retrieval

   An agent advertises describe_skill in its Agent Card.  A client
   invokes describe_skill to retrieve the validated Skill Interface
   Document for a selected advertised skill.  The operation retrieves
   the interface document; schema content identified by its Schema
   References is then obtained through the applicable schema-resolution
   mechanism.

5.  Terminology

5.1.  Network Management Agent

   A software component that performs or assists with network-management
   work, including analysis, configuration, assurance, incident
   handling, validation, simulation, or remediation.

5.2.  Client Agent

   An A2A Client that identifies and contacts a remote agent, obtains
   and validates its Skill Interface Documents, and delegates tasks on
   behalf of a user or another system.  This term describes a protocol
   role and does not imply administrative control over the remote agent.

5.3.  Remote Agent

   An A2A Server that publishes an Agent Card, exposes skills, receives
   delegated tasks, and returns task status and results.

5.4.  Schema Reference

   A portable schema identity plus integrity and resolution information.
   A Schema Reference identifies schema content independently of the
   mechanism used by a particular deployment to retrieve it.

5.5.  Schema Bundle

   An optional, signed or otherwise integrity-protected collection of
   schemas and a manifest distributed with an agent release.

5.6.  Schema Registry

   An optional deployment service that stores, versions, retrieves, and
   may check compatibility among schemas.  Registry-local identifiers
   are not portable schema identities.

5.7.  Skill

   A named capability advertised by an agent and invokable through an
   Agent-to-Agent protocol.

5.8.  Skill Interface Schema

   The standardized, language-neutral schema that defines the permitted
   structure and interpretation of a Skill Interface Document.  An agent
   uses a local or otherwise trusted copy of this schema to validate the
   documents it publishes.  A client agent uses the same schema version
   to validate retrieved documents.

5.9.  Skill Interface Document

   A machine-readable description of a skill's accepted input, produced
   output, possible supporting records, interaction behavior, and
   applicable constraints.  It is an instance of the Skill Interface
   Schema.  It contains domain-specific Schema References supplied by
   the agent without modifying the standardized Skill Interface Schema.

5.10.  Supporting Record

   A domain-specific observation or artifact used to derive, validate,
   reproduce, or audit a skill output.  A supporting record is validated
   against the applicable schema identified by the Skill Interface
   Document.

6.  Design Principles

6.1.  Separate transport from application semantics

   The Agent-to-Agent protocol owns task submission, protocol task
   identifiers, context identifiers, lifecycle state, streaming,
   polling, and cancellation.  The schema-interface framework owns the
   structure and meaning of the application payload.

   An application payload MUST NOT redefine an Agent-to-Agent task
   identifier as another unqualified task_id.  An application MAY carry
   a workflow_id, step_id, attempt_id, or explicitly named
   parent_a2a_task_id for correlation.

6.2.  Standardize reusable structures, not all domain semantics

   The common standard defines the Skill Interface Schema and Schema
   Reference.  A vendor or domain owner defines the input, output, and
   supporting-record schemas used by a particular skill.  A conforming
   implementation combines those domain schemas with the common
   structure to produce a Skill Interface Document; it does not redefine
   the common structure.

6.3.  Distinguish structural conformance from semantic conformance

   Matching Schema References establishes that communicating agents use
   the same schema; it does not establish that the schema exposes
   sufficient semantics for the intended operation.  A schema that
   defines configuration only as a string can validate the presence and
   type of that string but cannot by itself identify affected resources,
   validate command dependencies, or establish that the commands
   implement the requested intent.

   When a receiving agent is expected to inspect, validate, transform,
   simulate, or apply a configuration change, the shared domain schema
   MUST define a normalized structured representation of that change.
   The receiving agent MUST validate the representation and use a
   domain-specific implementation for semantic validation, policy
   evaluation, simulation, or application, as applicable.

   Device-specific rendering is a local implementation responsibility of
   the agent that requires it.  Rendered CLI is not part of the common
   operational representation exchanged between agents, and
   communicating agents are not required to agree on a rendered syntax
   or platform-specific command language.

   The applicable input, output, or supporting-record schema defines the
   normalized structure for a particular skill.  The describe_skill
   operation makes those requirements available before a client agent
   delegates work.

6.4.  Treat schema resolution as deployment-specific

   The stable schema identity and digest remain the same across
   deployments.  A customer deployment may resolve that identity from a
   registry, offline bundle, agent endpoint, inline schema, or trusted
   local cache.

6.5.  Keep the registry optional

   The remote agent and client agent MUST be capable of interoperating
   without a schema registry when the necessary schemas are supplied
   through another supported resolution mechanism.

6.6.  Distinguish outputs from supporting records

   The skill output states what the agent concluded or delivered.
   Supporting records explain why that output can be trusted,
   reproduced, or audited.  An artifact MAY be both output and a
   supporting record; implementations SHOULD avoid duplicating its
   content when the applicable domain schemas permit stable references.

6.7.  Assemble and validate before advertisement

   An agent implementation owns its domain-specific input, output, and
   supporting-record schemas.  Its protocol service combines those
   schemas with a trusted copy of the standardized Skill Interface
   Schema and applicable interaction and authority declarations.  The
   resulting Skill Interface Document MUST be validated before it is
   advertised or returned.

   An implementation SHOULD perform this assembly during agent
   initialization or deployment configuration and retain an immutable
   validated document for each skill version.  The describe_skill
   operation retrieves that document.  It does not ask the agent's
   domain logic to construct or alter an interface while processing the
   interface request.

7.  Schema Reference

   This document standardizes one Schema Reference structure for all
   schema roles.  Skill-input, skill-output, and supporting-record
   schemas do not require different reference structures, registries, or
   resolution mechanisms.

   A Schema Reference contains:

   *  schema_uri: stable portable identity;

   *  version: version meaningful to the schema publisher;

   *  dialect: schema language and version;

   *  digest: digest of the resolved schema content; and

   *  resolution: deployment-selected resolution information.

   json { "schema_uri": "urn:example:network-management:skill-
   input:1.0", "version": "1.0", "dialect": "https://json-schema.org/
   draft/2020-12/schema", "digest": "sha256:abc123...", "resolution": {
   "type": "inline", "schema": { "type": "object", "properties": {
   "objective": { "type": "string" } }, "required": [ "objective" ],
   "additionalProperties": false } } }

   When registry resolution is used, registry-local numeric identifiers
   MUST NOT be treated as globally portable schema identities.  Two
   registries may assign the same numeric identifier to different schema
   content.  A registry reference therefore includes the stable schema
   URI and digest.

8.  Skill Interface Schema and Documents

   The Skill Interface Schema standardizes the structure shown in this
   section.  A Skill Interface Document is a conforming instance for one
   skill version.  It binds the domain schemas used by that skill to its
   input, output, supporting-record, interaction, and authority
   characteristics.

   The agent or domain owner supplies the skill identifier, skill
   version, and domain input, output, and supporting-record schemas.
   The agent protocol service assembles the complete document.
   Interaction declarations reflect the agent implementation.  Authority
   declarations may additionally reflect deployment policy.  Assembly
   MUST NOT modify the standardized Skill Interface Schema.

   The following non-normative example illustrates a conforming Skill
   Interface Document using inline schema resolution:

   json { "interface_version": "1.0", "skill_id": "example_skill",
   "skill_version": "1.0", "input_schema": { "schema_uri":
   "urn:example:network-management:example-skill-input:1.0", "version":
   "1.0", "dialect": "https://json-schema.org/draft/2020-12/schema",
   "digest":
   "sha256:04f6775d30ad5d0f6661a7741f2da3a8dd3918938219d0f815c6a9e6009cb606",
   "resolution": { "type": "inline", "schema": { "type": "object",
   "properties": { "objective": { "type": "string" }, "constraints": {
   "type": "object", "description": "Skill-specific constraints defined
   by the domain schema." } }, "required": [ "objective" ],
   "additionalProperties": false } } }, "output_schema": { "schema_uri":
   "urn:example:network-management:example-skill-output:1.0", "version":
   "1.0", "dialect": "https://json-schema.org/draft/2020-12/schema",
   "digest":
   "sha256:9a16baf78ac2b47ca47423709257463d3d315b3e35be9b5d72b9fb0b1a9910ed",
   "resolution": { "type": "inline", "schema": { "type": "object",
   "properties": { "status": { "type": "string" } }, "required": [
   "status" ] } } }, "supporting_record_schemas": [ { "kind":
   "observation-record", "schema_uri": "urn:example:network-
   management:observation-record:1.0", "version": "1.0", "dialect":
   "https://json-schema.org/draft/2020-12/schema", "digest":
   "sha256:a2c799262a3ce3c19ef5cdd983bf3d12b43ab3c426227091b909dcb7054738c0",
   "resolution": { "type": "inline", "schema": { "type": "object" } } }
   ], "interaction": { "supported_response_modes": [ "sync", "stream",
   "poll" ], "cancellable": true }, "authority": { "default_mode":
   "read-only", "approval_may_be_required": true } }

   The inline schemas above are domain content populated into the
   standardized document.  They are not additions to or replacements for
   the Skill Interface Schema.  A deployment may instead populate the
   same Schema References with an agent-hosted, bundle, or registry
   resolution mechanism supported by the selected interface version.

   The Agent-to-Agent binding identifies the message part or data member
   that contains the skill input.  That input is validated against the
   domain input_schema.  Output and supporting-record validation follow
   the same model.

   Successful schema validation does not authorize execution.  The
   receiving agent and hosting platform MUST independently authenticate
   the caller and authorize the requested skill, resources, and
   operation.

8.1.  Skill input

   The skill input is the domain-specific application data submitted to
   a skill invocation.  The Agent-to-Agent binding identifies the
   message part or data member that contains this input, and the input
   MUST validate against the input_schema in the selected Skill
   Interface Document.  This document does not define an additional
   common request envelope around that data.  The Agent-to-Agent
   protocol remains authoritative for protocol task identity, context,
   lifecycle state, and transport.

   Constraints that affect skill execution MUST be represented in and
   validated by the skill's input_schema.  A receiving agent MUST
   enforce a supplied constraint or reject the invocation with a
   machine-readable error; it MUST NOT silently ignore a valid
   constraint.  Constraints enforced solely by a delegating system need
   not be transmitted.  The names, structures, and semantics of
   transmitted constraints are defined by the domain-specific input
   schema rather than by this framework.  Protocol lifecycle and
   authorization controls remain the responsibility of the Agent-to-
   Agent binding and deployment policy.

8.2.  Skill output

   The skill output is the domain-specific application data produced by
   a skill invocation.  The Agent-to-Agent binding identifies the
   message part or artifact data that contains this output, and the
   output MUST validate against the output_schema in the selected Skill
   Interface Document.  This document does not define an additional
   common output envelope around that data.

   Protocol task status indicates whether protocol execution completed;
   it is not part of the skill output.  Completion of a protocol task
   does not by itself establish that a requested downstream network
   operation completed successfully.  The domain output schema defines
   how the skill reports the result of that operation.

8.3.  Supporting-record schemas

   A supporting record is a domain-specific observation or artifact used
   to derive, validate, reproduce, or audit a skill output.  Each entry
   in supporting_record_schemas associates a kind with the Schema
   Reference for the complete record.  A produced record MUST validate
   against the schema for its identified kind.  A protocol progress
   update is not a supporting record unless it is published in that form
   and passes this validation.

   This framework does not define an additional common record envelope.
   The domain schema defines any required record identifier, producer,
   source, observation time, production time, integrity, derivation,
   classification, or payload fields.  Association with an Agent-to-
   Agent task or context is carried by the protocol binding and need not
   be duplicated in the record.  A deployment MAY attach additional
   correlation metadata when application-level workflow correlation is
   required.

   The skill output is the answer, decision, or deliverable normally
   consumed by the caller.  Supporting records contain the observations
   and artifacts that support that output.  An artifact MAY be both
   output and a supporting record; implementations SHOULD publish it
   once and use a stable reference when the applicable domain schemas
   permit that relationship.

9.  Skill Interface Advertisement and Retrieval

   This section defines the standardized procedure for advertising
   describe_skill and retrieving a Skill Interface Document for a
   selected skill.

9.1.  Agent advertisement

   An agent conforming to this framework MUST advertise describe_skill
   as a skill in its Agent Card.  The Agent Card also advertises the
   domain skills that can be selected in a describe_skill request.  The
   describe_skill skill MUST accept structured input identifying the
   selected skill_id and MUST produce structured output containing the
   corresponding Skill Interface Document.

   The advertisement identifies the supported Skill Interface version
   and advertised skill versions.  It SHOULD also provide an interface-
   document digest when the Agent Card representation permits that
   binding.

   A caller MUST NOT assume that every Agent-to-Agent implementation
   conforms to this framework.  Absence of the describe_skill skill from
   the Agent Card means that the agent does not provide the schema-
   interface procedure defined here.  Such an agent MAY still be invoked
   using the base Agent-to-Agent protocol or an explicitly configured
   out-of-band interface contract.  The caller MUST NOT infer or
   prescribe the remote skill's domain schemas from skill descriptions
   or media types alone, and MUST NOT claim schema-interface conformance
   or schema-governed compatibility for such an invocation.  Supporting
   multiple non-conforming agents requires separately configured
   contracts, adapters, or other bilateral integration mechanisms.  This
   is the scaling problem addressed by this document: replacing an
   expanding collection of bilateral integrations with one standardized
   interface-retrieval procedure.

9.2.  describe_skill request

   The request selects one advertised skill:

   json { "skill": "describe_skill", "arguments": { "skill_id":
   "example_skill" } }

9.3.  describe_skill response

   The response is a Skill Interface Document conforming to the
   advertised version of the standardized Skill Interface Schema.  It
   MAY contain complete domain schemas inline or MAY contain Schema
   References resolved through another supported mechanism.

   The response MUST be the previously assembled and validated document
   for the selected skill version.  The describe_skill operation MUST
   NOT redefine the standard structure or invoke domain logic to
   construct or modify the document while processing the request.  The
   returned input, output, and supporting-record schemas remain specific
   to the selected agent and skill.

   The selected document MUST correspond to the skill version advertised
   by the agent.  If the agent cannot provide a conforming compatible
   document, it MUST fail the request with a machine-readable error
   rather than accepting an unvalidated opaque payload.

9.4.  Client-agent behavior

   The following figure illustrates the initial inline flow between a
   client agent and a remote network management agent.  Inline delivery
   does not replace Schema References.  Each reference retains its
   stable identity, version, dialect, and digest while carrying the
   schema content in its resolution field.

          Client Agent                         Remote Agent
               |                                    |
               |------ Retrieve Agent Card -------->|
               |<----- Skills and A2A endpoint -----|
               |                                    |
               |--- describe_skill(skill_id) ------>|
               |<-- Skill Interface Document -------|
               |       Schema References:           |
               |       - input schema               |
               |       - output schema              |
               |       - supporting records         |
               |       resolution.type = inline     |
               |       embedded schema content      |
               |                                    |
               | Validate interface structure,      |
               | references, digests, and schemas   |
               |                                    |
               |--- Delegate validated request ---->|
               |<--- Status, output, and records ---|
               | Validate response using cached     |
               | Schema References                  |

   For inline resolution, the client verifies each embedded schema
   against the digest declared by its Schema Reference before using it.
   Other resolution mechanisms are specified in Section 11.  The
   following steps define the client behavior for all supported
   resolution mechanisms.

   A client agent performs the following sequence:

   1.   retrieve the target Agent Card and obtain its A2A endpoint,
        agent version, and advertised skill identifiers;

   2.   verify that both describe_skill and the selected domain skill
        are advertised;

   3.   call describe_skill for the selected skill;

   4.   validate the returned Skill Interface Document against a trusted
        local copy of the selected Skill Interface Schema;

   5.   verify and, when necessary, resolve the referenced domain
        schemas;

   6.   validate the outgoing skill input against input_schema;

   7.   delegate the task through the Agent-to-Agent protocol;

   8.   receive task status, typed skill output, and supporting records;

   9.   validate the skill output against output_schema and validate the
        supporting records; and

   10.  preserve, forward, display, or interpret them according to local
        policy.

   Before delegating a domain skill under this framework, the client
   agent MUST possess a successfully validated Skill Interface Document
   obtained from that target's describe_skill skill.  If describe_skill
   is absent, fails, returns a document for a different skill or
   version, or returns a document that cannot be validated, the client
   agent MUST NOT delegate the domain request using the procedure
   defined in this document.

   The client agent MAY reuse a cached Skill Interface Document without
   calling describe_skill before every task when the cache entry is
   bound to the same target identity, agent version, skill identifier,
   skill version, and, when advertised, interface-document digest.  A
   change to any of those values invalidates the entry and requires a
   new describe_skill exchange before the next delegation.

   A generic client agent can validate and route an unfamiliar vendor
   schema without understanding its domain semantics.  A domain-aware
   orchestrator may install optional handlers keyed by stable schema URI
   to evaluate operational thresholds, incident records, configuration
   policy, or other domain behavior.

9.5.  Composition of consecutive skills

   When the output of one skill becomes the input to another skill, the
   component initiating the downstream delegation is the client agent
   for that interaction.  That component may be a centralized
   orchestrator or the upstream agent itself communicating directly with
   the downstream agent.  The same composition rules apply in either
   topology.

   The following figure shows the reference comparison and validation
   decisions performed by that delegating component.

    Upstream Agent                 Delegating Component
          |                                  |
          |-- Output payload ---------------->|
          |   output_schema reference        |
          |                                  |
          |                         Retrieve downstream
          |                         Skill Interface
          |                                  |
          |                                  v
          |                         Downstream input_schema
          |                              reference
          |                                  |
          |                    Compare URI, version,
          |                    dialect, and digest
          |                                  |
          |                +-----------------+----------------+
          |                |                                  |
          |              Match                         No exact match
          |                |                                  |
          |      Validate output against              Reject direct
          |      downstream input schema               composition
          |                |
          |                v
          |      Delegate validated input
          |                |
          |                v
          |        Downstream Agent
          |      validates and processes

   The standardized Schema Reference allows an orchestrating system or
   delegating agent to determine structural compatibility without
   interpreting a domain-specific schema.  Direct composition MUST
   require the Schema Reference for the transferred upstream output
   payload and the Schema Reference accepted for the corresponding
   downstream input to have the same schema_uri, version, dialect, and
   digest.  Their deployment-specific resolution information need not
   match.

   The orchestrating system or delegating agent MUST validate the
   transferred instance mechanically against the downstream input schema
   before delegation, and the receiving agent MUST validate the received
   instance before processing it.  Neither operation requires the
   orchestrating system or delegating agent to understand the schema's
   domain semantics.

   If those Schema Reference fields do not match, the delegating
   component MUST NOT perform direct composition under this
   specification.

   An implementation can use an out-of-band transformation mechanism
   before delegation.  Transformation discovery, trust, execution, and
   provenance are outside the scope of this document.  Any resulting
   payload enters this procedure as a new input and is subject to
   ordinary input validation against the downstream input_schema.

   Matching Schema References and successful instance validation
   establish structural compatibility, not operational correctness.  The
   receiving agent remains responsible for domain-semantic validation,
   authorization, policy evaluation, and operational safety before
   acting on the input.

10.  Schema Publication and Packaging

10.1.  Vendor release artifacts

   Agent domain schemas are deployment-independent source artifacts.
   The standardized Skill Interface Schema is a separately versioned
   common artifact; an implementation packages an exact trusted copy
   rather than maintaining an agent-specific variation.  A vendor
   release pipeline SHOULD:

   1.  validate all schemas;

   2.  test representative inputs and outputs against them;

   3.  assign stable schema URIs and versions;

   4.  compute schema digests;

   5.  when publishing a schema bundle, produce a bundle manifest; and

   6.  sign or otherwise integrity-protect any published schema bundle.

   Producing a schema bundle is optional.  For example, an
   implementation using inline resolution can embed its schemas in the
   agent artifact without publishing a separate bundle.  The pipeline
   does not need access to a customer registry.

10.2.  Agent initialization

   Before advertising schema-interface support, an agent SHOULD:

   1.  load and integrity-check its packaged Skill Interface Schema;

   2.  load its domain input, output, and supporting-record schemas;

   3.  assemble a Skill Interface Document for each advertised skill
       version;

   4.  validate each document and each inline schema digest; and

   5.  retain an immutable validated representation for describe_skill.

   Failure to load, assemble, or validate an interface prevents that
   skill version from being advertised through this framework.  An
   implementation MUST NOT silently fall back to an opaque unconstrained
   payload.

11.  Schema Resolution

11.1.  Trusted cache

   A client agent SHOULD cache verified schema content by stable schema
   URI and digest.  A cached schema may be used while a registry or
   agent schema endpoint is temporarily unavailable.

11.2.  Optional schema registry

   A registry may provide centralized storage, subject versioning,
   references, compatibility checks, publisher metadata, and governance.
   [CONFLUENT] is one non-normative example of this class of service.
   The standard does not require a particular registry implementation or
   REST API.

   When a registry is used, the deployment creates a local mapping from
   stable schema URI and digest to registry subject, version, and
   identifier.  That mapping is supplied to the agent or made available
   to the client agent.

   An agent identifies a registry by a logical deployment name.  The
   client agent maps that name to an administrator-configured trusted
   endpoint.  A client agent MUST NOT retrieve schemas from an arbitrary
   registry URL supplied in an untrusted task payload.

11.3.  Agent-hosted schemas

   An agent MAY expose packaged schemas beneath a well-known path
   associated with the already identified and authenticated agent
   endpoint.  A Schema Reference using this mechanism contains a
   relative path and digest.  It does not redirect the client agent to
   an arbitrary host.

11.4.  Inline schemas

   describe_skill MAY return schemas inline.  Inline resolution is
   suitable for small skill interfaces, local development, and
   deployments without a registry.  The client agent still verifies the
   declared digest and applies publisher and size policy.

11.5.  Offline bundle

   An air-gapped deployment MAY install an approved schema bundle
   alongside the client agent.  The client agent resolves stable schema
   URIs from that bundle without network access.

11.6.  Resolution policy

   A deployment determines which schema-resolution mechanisms are
   permitted and how an available mechanism is selected.  This document
   does not define a priority or fallback order among resolution
   mechanisms.  Regardless of the mechanism used, the client agent
   verifies that the resolved schema matches the identity and digest in
   the Schema Reference.

12.  Schema Evolution and Compatibility

   Schema publishers MUST treat a published schema version and digest as
   immutable.  A changed schema receives a new version and digest.

   Compatibility policy SHOULD be applied to a governed schema family.
   Structural compatibility checking is necessary but not sufficient.
   It cannot establish that units, operational interpretation,
   authority, or supporting-record quality remain compatible.

   A breaking semantic change requires a new major version even if a
   structural JSON Schema checker accepts the change.  Examples include:

   *  changing a utilization value from percent to a fraction;

   *  changing a timestamp from observation time to processing time;

   *  changing a supporting-record classification from authoritative to
      inferred; or

   *  changing a configuration artifact from candidate to applied state.

   The Skill Interface Document MUST identify the exact schema versions
   currently used by the skill.  A caller MUST NOT substitute a
   registry's mutable latest version after accepting a document.

13.  Security Considerations

13.1.  Schema trust

   A syntactically valid schema is not necessarily trustworthy.  A
   client agent applies policy for trusted publishers, schema
   identities, digests, versions, dialects, and resolution mechanisms.

13.2.  Arbitrary retrieval

   Following arbitrary schema URLs can expose a client agent to server-
   side request forgery, credential leakage, malicious redirects, and
   availability attacks.  Registry aliases and agent-relative paths are
   resolved only through trusted, administrator-configured endpoints.

13.3.  Resource limits

   A client agent enforces limits on schema size, nesting, reference
   depth, reference cycles, compilation time, payload size, and cache
   consumption.

13.4.  Schema validation and authorization

   Schema validation establishes structural conformance, not caller
   authority, operational safety, truth, or permission to modify a
   network.  Authorization and policy checks occur at execution time.

13.5.  Supporting-record integrity and provenance

   Supporting records can be stale, replayed, forged, selectively
   omitted, or derived from untrusted inputs.  A supporting-record
   schema SHOULD require the source, producer, relevant observation and
   production times, integrity data, derivation, and classification
   needed by its domain.  Deployments define freshness and retention
   policy appropriate to the operation.

13.6.  Injection

   Text, CLI configuration, tool output, model output, and supporting-
   record payloads are untrusted data.  An agent does not treat
   instructions embedded in those artifacts as authorized task
   instructions unless the applicable schema and policy explicitly
   assign them that role.

13.7.  Interface integrity and substitution

   The remote agent and client agent MUST integrity-check the packaged
   Skill Interface Schema before using it.  A local implementation MUST
   NOT modify the standardized schema while adding domain schemas.

   A client agent verifies that a retrieved Skill Interface Document
   identifies the requested agent skill and advertised skill version.
   It validates the document against the selected Skill Interface Schema
   and verifies all resolved schema digests.  A structurally valid
   document for a different skill or version MUST NOT be accepted as a
   substitute.

14.  Operational Considerations

   Interface retrieval and schema resolution SHOULD NOT add a
   describe_skill or registry lookup to every task.  A client agent
   caches validated Skill Interface Documents, verified domain schemas,
   and compiled validators.  A cache entry is bound to the agent
   identity, skill identifier, skill version, interface version, and,
   when advertised, interface-document digest.  A changed advertised
   version or digest invalidates the corresponding entry.

   An implementation SHOULD expose diagnostics identifying:

   *  the Skill Interface Schema version and skill version selected;

   *  schema URIs, versions, and digests used;

   *  the resolution mechanism used for each schema;

   *  validation failures;

   *  unavailable or untrusted schemas; and

   *  compatibility or policy failures.

   Deployments SHOULD test operation during temporary registry
   unavailability and SHOULD define cache refresh and schema-revocation
   behavior.

15.  IANA Considerations

   This early version does not request any IANA actions.  A later
   version may request identifiers for Skill Interface versions, media
   types, or URN namespaces after the representation and protocol
   mapping stabilize.

16.  Open Issues

   The following issues require further review:

   1.  version-negotiation behavior when multiple interface versions are
       supported;

   2.  representation of confidential supporting records and access-
       controlled artifact references;

   3.  schema revocation and emergency withdrawal;

   4.  signature format for schema bundles and Skill Interface
       Documents; and

   5.  mapping to existing schema registries without making a registry
       API normative.
