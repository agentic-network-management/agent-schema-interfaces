Schema Interfaces for Network Management Agent Skills

Abstract

Network management agents can use an Agent-to-Agent protocol to discover peers, delegate work, observe task state, receive results, and cancel work. The protocol alone does not define the application schemas used by an analysis agent, incident-analysis agent, configuration agent, or other independently developed network management agent.¶

This document standardizes three components for the machine-readable schema interfaces of network management agent skills: a Schema Reference structure for identifying, verifying, and carrying schemas; a Skill Interface Schema and conforming per-skill Skill Interface Document; and a Skill Interface advertisement and retrieval procedure using describe_skill. The Skill Interface combines the input, output, and supporting-record schemas defined by the agent's vendor or domain owner with common interaction and authority declarations.¶

Version 1.0 standardizes inline schema delivery. Every Schema Reference returned by describe_skill carries its schema content and a digest for verifying that content. Registries, bundles, caches, and agent packaging may be used as deployment-local management and governance mechanisms, but they are not alternative v1.0 wire-resolution forms or runtime dependencies for a client agent.¶

1. Introduction

Agent-to-Agent task exchange requires agreement at two different layers:¶

  1. a protocol for agent discovery, task identity, lifecycle, streaming, polling, cancellation, and result transport; and¶

  2. application schemas that define the meaning of the skill input, output, deliverables, and supporting records.¶

The Agent2Agent (A2A) protocol [A2A] defines agent discovery, message transport, task lifecycle, streaming, polling, cancellation, and artifact delivery. It does not define the domain-specific input, output, or supporting-record schemas used by individual skills, nor a common interface for retrieving and validating those schemas. This document addresses that application-schema gap while leaving A2A task and transport semantics unchanged.¶

Agent discovery and the schema-interface procedure are distinct. Agent discovery determines which agent to contact and how to reach it. The schema-interface procedure defined in this document occurs after an agent has been identified and provides the machine-readable interface for invoking one of its advertised skills. This document does not define how agents are found, selected, ranked, or matched to user intent.¶

A common protocol envelope can deliver a JSON object without making that object semantically interoperable. If the original input and an upstream agent's result are opaque text or unconstrained JSON, a downstream agent must infer their meaning. Such inference may be useful for human-oriented content, but it is not an adequate substitute for a declared interface when agents make operational decisions or generate network changes.¶

The three standardized components define a framework in which:¶

  • common Schema Reference and Skill Interface structures are standardized without standardizing every domain payload;¶

  • each skill declares versioned input, output, and supporting-record schemas;¶

  • vendors and domain owners define the schemas specific to their agents;¶

  • an agent assembles and validates a Skill Interface Document from the common structure and its domain schemas before advertising that document;¶

  • a client agent retrieves and validates the selected Skill Interface before delegation;¶

  • schemas are delivered inline without assuming a particular registry product; and¶

  • skill outputs and their supporting records can be validated before they are consumed or acted upon.¶

The framework is intended to support independently developed agents from different network-management domains without forcing their domain payloads into one universal schema.¶

2. Relationship to Other Work

The "IDL: A Semantic Information Model for Agent Communication" Internet-Draft [IDL] describes agent-wide identity, capabilities, autonomy boundaries, context requirements, governance interfaces, and intent participation. It includes optional input-context and output-schema declarations, but it does not define a normative serialization or a per-skill interface-retrieval procedure.¶

This document has a narrower scope. It defines a normative representation for one version of one callable skill, including its input, output, and supporting-record schemas, and defines the describe_skill retrieval and validation procedure. The two models can be used together: an agent-wide semantic description can identify a capability, while a Skill Interface Document supplies the concrete application schemas used to invoke a selected skill. A formal mapping between the two models is outside the scope of this document.¶

4. Scope

This document standardizes:¶

  • a common Schema Reference structure for identifying, verifying, and carrying inline schemas;¶

  • a Skill Interface Schema and a conforming per-skill Skill Interface Document; and¶

  • a Skill Interface advertisement and retrieval procedure using describe_skill.¶

In support of those three components, this document also defines:¶

  • the relationship among skill inputs, skill outputs, and supporting records;¶

  • schema identity, integrity, versioning, and inline delivery behavior;¶

  • the relationship between these interfaces and Agent-to-Agent task state; and¶

  • requirements for validation, caching, trust, and failure handling.¶

This document does not define:¶

  • the internal algorithm used by an agent;¶

  • a universal schema for every network-management domain;¶

  • the concrete mapping of describe_skill, skill input, skill output, or supporting records to A2A messages, Parts, artifacts, metadata, or extension elements;¶

  • a required schema-registry product or API;¶

  • a globally centralized schema service;¶

  • agent hosting, process lifecycle, or platform onboarding;¶

  • an authorization policy model, including RBAC, ABAC, capabilities, policy engines, or approval workflows;¶

  • a grant of authority based on schema or interface validation; or¶

  • the semantics of vendor-specific analysis, incident, or configuration data.¶

A conforming A2A Binding Profile or deployment specification MUST define those protocol mappings before this framework is used over A2A. Conformance to this document alone establishes schema-interface conformance; it does not establish end-to-end A2A wire interoperability.¶

5. Standardized Components

5.1. Schema Reference Structure

The Schema Reference is a common structure for identifying a schema by stable URI and version, declaring its schema dialect, verifying its content by digest, and carrying that content inline. The same structure is used for input, output, and supporting-record schemas. The structure is standardized so that a client can identify and verify every schema in a Skill Interface without agent-specific or registry-specific interpretation. Version 1.0 does not define an external schema-retrieval mechanism.¶

A standardized Schema Reference also enables composition across independently developed agents. An orchestrating system or delegating agent can compare the Schema Reference of an upstream output payload with the Schema Reference accepted for a downstream input without interpreting either schema's domain semantics. Matching schema identity, version, dialect, and digest provides a deterministic basis for deciding whether direct composition is permitted.¶

5.2. Skill Interface

The Skill Interface Schema defines the common structure of a Skill Interface Document. A conforming document describes one version of one skill and binds the domain-specific input, output, and supporting-record schemas used by that skill to common interaction and authority declarations.¶

5.3. Skill Interface Advertisement and Retrieval

An agent advertises describe_skill in its Agent Card. A client invokes describe_skill to retrieve the validated Skill Interface Document for a selected advertised skill. The operation retrieves the interface document; each Schema Reference in that document includes its schema content inline.¶

6. Terminology

6.1. Network Management Agent

A software component that performs or assists with network-management work, including analysis, configuration, assurance, incident handling, validation, simulation, or remediation.¶

6.2. Client Agent

An A2A Client that identifies and contacts a remote agent, obtains and validates its Skill Interface Documents, and delegates tasks on behalf of a user or another system. This term describes a protocol role and does not imply administrative control over the remote agent.¶

6.3. Remote Agent

An A2A Server that publishes an Agent Card, exposes skills, receives delegated tasks, and returns task status and results.¶

6.4. A2A Binding Profile

A specification that maps the abstract operations and application data defined by this document to concrete A2A protocol elements. It identifies how describe_skill requests and responses, skill inputs, skill outputs, and supporting records are carried in A2A messages, Parts, artifacts, metadata, or extension elements. A deployment specification may define such a mapping for local use.¶

6.5. Schema Reference

A portable schema identity, integrity information, and inline schema content. The identity and digest remain independent of any deployment-local mechanism used to manage the schema before the Skill Interface Document is assembled.¶

6.6. Schema Bundle

An optional, signed or otherwise integrity-protected collection of schemas and a manifest distributed with an agent release. A bundle may supply schemas to an agent during interface assembly, but it is not referenced on the v1.0 wire.¶

6.7. Schema Registry

An optional deployment service that stores, versions, retrieves, and may check compatibility among schemas. It is a deployment-local management and governance mechanism, not a v1.0 schema-delivery mechanism between agents. Registry-local identifiers are not portable schema identities.¶

6.8. Skill

A named capability advertised by an agent and invokable through an Agent-to-Agent protocol.¶

6.9. Skill Interface Schema

The standardized, language-neutral schema that defines the permitted structure and interpretation of a Skill Interface Document. An agent uses a local or otherwise trusted copy of this schema to validate the documents it publishes. A client agent uses the same schema version to validate retrieved documents.¶

6.10. Skill Interface Document

A machine-readable description of a skill's accepted input, produced output, possible supporting records, interaction behavior, and applicable constraints. It is an instance of the Skill Interface Schema. It contains domain-specific Schema References supplied by the agent without modifying the standardized Skill Interface Schema.¶

6.11. Supporting Record

A domain-specific observation or artifact used to derive, validate, reproduce, or audit a skill output. A supporting record is validated against the applicable schema identified by the Skill Interface Document.¶

7. Design Principles

7.1. Separate transport from application semantics

The Agent-to-Agent protocol owns task submission, protocol task identifiers, context identifiers, lifecycle state, streaming, polling, and cancellation. The schema-interface framework owns the structure and meaning of the application payload.¶

This document does not select the A2A protocol elements that carry those application payloads. A conforming A2A Binding Profile or deployment specification MUST define that mapping. A deployment-local mapping can enable interoperation within that deployment, but it does not by itself define a portable binding for independently implemented agents.¶

An application payload MUST NOT redefine an Agent-to-Agent task identifier as another unqualified task_id. An application MAY carry a workflow_id, step_id, attempt_id, or explicitly named parent_a2a_task_id for correlation.¶

Each delegation hop creates a separate Agent-to-Agent task at the receiving agent. A delegating component MUST NOT reuse an upstream task identifier as the downstream protocol task identifier. Protocol task identifiers are interpreted in the scope of the agent or endpoint that issued them; implementations MUST NOT assume that they are globally unique. Cross-hop correlation MUST use separately named metadata rather than overloading protocol task identifiers.¶

7.2. Standardize reusable structures, not all domain semantics

The common standard defines the Skill Interface Schema and Schema Reference. A vendor or domain owner defines the input, output, and supporting-record schemas used by a particular skill. A conforming implementation combines those domain schemas with the common structure to produce a Skill Interface Document; it does not redefine the common structure.¶

7.3. Distinguish structural conformance from semantic conformance

Matching Schema References establishes that communicating agents use the same schema; it does not establish that the schema exposes sufficient semantics for the intended operation. A schema that defines configuration only as a string can validate the presence and type of that string but cannot by itself identify affected resources, validate command dependencies, or establish that the commands implement the requested intent.¶

When a receiving agent is expected to inspect, validate, transform, simulate, or apply a configuration change, the shared domain schema MUST define a normalized structured representation of that change. The receiving agent MUST validate the representation and use a domain-specific implementation for semantic validation, policy evaluation, simulation, or application, as applicable.¶

Device-specific rendering is a local implementation responsibility of the agent that requires it. Rendered CLI is not part of the common operational representation exchanged between agents, and communicating agents are not required to agree on a rendered syntax or platform-specific command language.¶

The applicable input, output, or supporting-record schema defines the normalized structure for a particular skill. The describe_skill operation makes those requirements available before a client agent delegates work.¶

7.4. Deliver schemas inline in version 1.0

Every v1.0 Schema Reference returned by describe_skill MUST carry its schema content inline. A client agent validates that embedded content against the declared digest and does not contact an external service to complete the interface.¶

Registries, bundles, caches, and agent packaging MAY be used locally to store, govern, distribute, or prepare schemas. Their use does not alter the v1.0 wire representation, and a client agent is not required to know which local mechanism supplied an inline schema.¶

7.5. Distinguish outputs from supporting records

The skill output states what the agent concluded or delivered. Supporting records explain why that output can be trusted, reproduced, or audited. An artifact MAY be both output and a supporting record; implementations SHOULD avoid duplicating its content when the applicable domain schemas permit stable references.¶

7.6. Assemble and validate before advertisement

An agent implementation owns its domain-specific input, output, and supporting-record schemas. Its protocol service combines those schemas with a trusted copy of the standardized Skill Interface Schema and applicable interaction and authority declarations. The resulting Skill Interface Document MUST be validated before it is advertised or returned.¶

An implementation SHOULD perform this assembly during agent initialization or deployment configuration and retain an immutable validated document for each skill version. The describe_skill operation retrieves that document. It does not ask the agent's domain logic to construct or alter an interface while processing the interface request.¶

8. Schema Reference

This document standardizes one Schema Reference structure for all schema roles. Skill-input, skill-output, and supporting-record schemas do not require different reference structures or delivery mechanisms.¶

A Schema Reference contains:¶

  • schema_uri: stable portable identity;¶

  • version: version meaningful to the schema publisher;¶

  • dialect: schema language and version;¶

  • digest: digest of the embedded schema content; and¶

  • resolution: inline delivery information. In version 1.0 its type is inline and its schema member contains the schema content.¶

Version 1.0 fixes the digest algorithm to SHA-256. The digest value MUST be the lowercase string sha256: followed by exactly 64 lowercase hexadecimal digits representing the SHA-256 digest of the embedded schema content. Version 1.0 does not define digest-algorithm negotiation, and a value using another algorithm identifier is invalid.¶

json { "schema_uri": "urn:example:network-management:skill-input:1.0", "version": "1.0", "dialect": "https://json-schema.org/draft/2020-12/schema", "digest": "sha256:b521c98329fe028c3ca9b157a721c412a1a04ca5ba799ebe5a916e6355f84ff8", "resolution": { "type": "inline", "schema": { "type": "object", "properties": { "objective": { "type": "string" } }, "required": [ "objective" ], "additionalProperties": false } } } ¶

Version 1.0 Schema References MUST use resolution.type equal to inline and MUST include the schema in resolution.schema. They MUST NOT contain an external schema locator in place of the embedded content. A deployment may use a registry or another local source before assembling the document, but registry-local identifiers are not included in the v1.0 Schema Reference.¶

9. Skill Interface Schema and Documents

The Skill Interface Schema standardizes the structure shown in this section. A Skill Interface Document is a conforming instance for one skill version. It binds the domain schemas used by that skill to its input, output, supporting-record, interaction, and authority characteristics.¶

The agent or domain owner supplies the skill identifier, skill version, and domain input, output, and supporting-record schemas. The agent protocol service assembles the complete document. Interaction declarations reflect the agent implementation. Authority declarations may additionally reflect deployment policy. Assembly MUST NOT modify the standardized Skill Interface Schema.¶

The authority member is descriptive metadata about the operating posture an agent advertises for a skill. default_mode describes that advertised default posture; it does not grant the caller permission to use that mode. approval_may_be_required indicates that an approval requirement may apply; it does not assert that approval has been requested, granted, or remains valid. The authority member is not a credential, capability, entitlement, access-control decision, approval record, or authorization token. A client or remote agent MUST NOT treat it as permission to execute a skill or cause a side effect.¶

The following non-normative example illustrates a conforming Skill Interface Document using inline schema delivery:¶

json { "interface_version": "1.0", "skill_id": "example_skill", "skill_version": "1.0", "input_schema": { "schema_uri": "urn:example:network-management:example-skill-input:1.0", "version": "1.0", "dialect": "https://json-schema.org/draft/2020-12/schema", "digest": "sha256:04f6775d30ad5d0f6661a7741f2da3a8dd3918938219d0f815c6a9e6009cb606", "resolution": { "type": "inline", "schema": { "type": "object", "properties": { "objective": { "type": "string" }, "constraints": { "type": "object", "description": "Skill-specific constraints defined by the domain schema." } }, "required": [ "objective" ], "additionalProperties": false } } }, "output_schema": { "schema_uri": "urn:example:network-management:example-skill-output:1.0", "version": "1.0", "dialect": "https://json-schema.org/draft/2020-12/schema", "digest": "sha256:9a16baf78ac2b47ca47423709257463d3d315b3e35be9b5d72b9fb0b1a9910ed", "resolution": { "type": "inline", "schema": { "type": "object", "properties": { "status": { "type": "string" } }, "required": [ "status" ] } } }, "supporting_record_schemas": [ { "kind": "observation-record", "schema_reference": { "schema_uri": "urn:example:network-management:observation-record:1.0", "version": "1.0", "dialect": "https://json-schema.org/draft/2020-12/schema", "digest": "sha256:a2c799262a3ce3c19ef5cdd983bf3d12b43ab3c426227091b909dcb7054738c0", "resolution": { "type": "inline", "schema": { "type": "object" } } } } ], "interaction": { "supported_response_modes": [ "sync", "stream", "poll" ], "cancellable": true }, "authority": { "default_mode": "read-only", "approval_may_be_required": true } } ¶

The inline schemas above are domain content populated into the standardized document. They are not additions to or replacements for the Skill Interface Schema. Version 1.0 requires this domain content to be present inline. A deployment-local registry, bundle, cache, or package may supply the content when the agent assembles the document, but that source is not exposed as an alternative wire-resolution form.¶

A conforming A2A Binding Profile or deployment specification identifies the protocol element that contains the skill input. That input is validated against the domain input_schema. Output and supporting-record validation follow the same model.¶

Successful schema or Skill Interface validation does not authorize execution. Before processing an invocation, the receiving agent or hosting platform MUST authenticate the caller and perform a current authorization decision covering the requested skill, resources, operation, and applicable constraints. Before causing a side effect, it MUST also enforce any approval or execution-control requirements imposed by current deployment policy. Advertised authority metadata does not replace these runtime decisions.¶

9.1. Skill input

The skill input is the domain-specific application data submitted to a skill invocation. A conforming A2A Binding Profile or deployment specification MUST identify the protocol element containing this input. The input MUST validate against the input_schema in the selected Skill Interface Document. This document does not define an additional common request envelope around that data. The Agent-to-Agent protocol remains authoritative for protocol task identity, context, lifecycle state, and transport.¶

Constraints that affect skill execution MUST be represented in and validated by the skill's input_schema. A receiving agent MUST enforce a supplied constraint or reject the invocation with the constraint_rejected machine-readable error condition defined in Section 10.4; it MUST NOT silently ignore a valid constraint. Constraints enforced solely by a delegating system need not be transmitted. The names, structures, and semantics of transmitted constraints are defined by the domain-specific input schema rather than by this framework. Protocol lifecycle and authorization controls remain the responsibility of the A2A Binding Profile and deployment policy.¶

9.2. Skill output

The skill output is the domain-specific application data produced by a skill invocation. A conforming A2A Binding Profile or deployment specification MUST identify the protocol element containing this output. The output MUST validate against the output_schema in the selected Skill Interface Document. This document does not define an additional common output envelope around that data.¶

Protocol task status indicates whether protocol execution completed; it is not part of the skill output. Completion of a protocol task does not by itself establish that a requested downstream network operation completed successfully. The domain output schema defines how the skill reports the result of that operation.¶

9.3. Supporting-record schemas

A supporting record is a domain-specific observation or artifact used to derive, validate, reproduce, or audit a skill output. Each entry in supporting_record_schemas associates a kind with the Schema Reference for the complete record. A produced record MUST validate against the schema for its identified kind. A protocol progress update is not a supporting record unless it is published in that form and passes this validation.¶

This framework does not define an additional common record envelope. The domain schema defines any required record identifier, producer, source, observation time, production time, integrity, derivation, classification, or payload fields. Association with an Agent-to-Agent task or context is carried according to the A2A Binding Profile or deployment specification and need not be duplicated in the record. A deployment MAY attach additional correlation metadata when application-level workflow correlation is required.¶

When particular supporting records justify a result, conclusion, decision, or deliverable, the domain output_schema SHOULD define stable references from the output to those records. The domain schema or applicable A2A Binding Profile defines the reference syntax; this framework does not define a common claim or supporting-record envelope. A reference SHOULD identify the record unambiguously within its applicable scope and remain stable across retransmission and later retrieval of the same task result. It SHOULD NOT rely solely on array position, message ordering, or another transient transport location. The binding or deployment specification defines how a referenced record is carried or retrieved.¶

The skill output is the answer, decision, or deliverable normally consumed by the caller. Supporting records contain the observations and artifacts that support that output. An artifact MAY be both output and a supporting record; implementations SHOULD publish it once and reference it rather than duplicate its content when the applicable domain schemas permit that relationship.¶

10. Skill Interface Advertisement and Retrieval

This section defines the abstract procedure for advertising describe_skill and retrieving a Skill Interface Document for a selected skill. The concrete A2A representation of this procedure is defined by an A2A Binding Profile or deployment specification.¶

10.1. Agent advertisement

An agent conforming to this framework MUST advertise describe_skill as a skill in its Agent Card. The Agent Card also advertises the domain skills that can be selected in a describe_skill request. The describe_skill skill MUST accept structured input identifying the selected skill_id and MUST produce structured output containing the corresponding Skill Interface Document.¶

The advertisement identifies the supported Skill Interface version and advertised skill versions. It SHOULD also provide an interface-document digest when the selected A2A Binding Profile permits that representation.¶

A client MUST select the Skill Interface version and advertised domain-skill version from the advertisement before invoking describe_skill. Version 1.0 does not define request parameters for negotiating or selecting an interface version or skill version within describe_skill. The advertised selection therefore MUST identify one Skill Interface Document unambiguously. If an advertisement exposes multiple versions but the selected A2A Binding Profile or deployment specification does not define an unambiguous pre-request selection mechanism, the client MUST NOT use the version 1.0 retrieval procedure for that skill.¶

A caller MUST NOT assume that every Agent-to-Agent implementation conforms to this framework. Absence of the describe_skill skill from the Agent Card means that the agent does not provide the schema-interface procedure defined here. Such an agent MAY still be invoked using the base Agent-to-Agent protocol or an explicitly configured out-of-band interface contract. The caller MUST NOT infer or prescribe the remote skill's domain schemas from skill descriptions or media types alone, and MUST NOT claim schema-interface conformance or schema-governed compatibility for such an invocation. Supporting multiple non-conforming agents requires separately configured contracts, adapters, or other bilateral integration mechanisms. This is the scaling problem addressed by this document: replacing an expanding collection of bilateral integrations with one standardized interface-retrieval procedure.¶

10.2. describe_skill request

After version selection, the request identifies one advertised skill by skill_id. It does not carry interface_version, skill_version, a version range, or another in-band negotiation parameter. The following JSON object represents the application data, not a complete A2A message or JSON-RPC request:¶

json { "skill": "describe_skill", "arguments": { "skill_id": "example_skill" } } ¶

10.3. describe_skill response

The response is a Skill Interface Document conforming to the advertised and previously selected version of the standardized Skill Interface Schema. Its skill_version MUST equal the advertised domain-skill version selected before the request. In version 1.0, every Schema Reference in the response MUST contain the complete domain schema inline in resolution.schema and MUST set resolution.type to inline.¶

The Skill Interface Document is the application data returned by the abstract operation; the selected A2A Binding Profile or deployment specification defines the protocol element that carries it.¶

The response MUST be the previously assembled and validated document for the selected skill version. The describe_skill operation MUST NOT redefine the standard structure or invoke domain logic to construct or modify the document while processing the request. The returned input, output, and supporting-record schemas remain specific to the selected agent and skill.¶

The selected document MUST correspond to the skill version advertised by the agent. If an advertised interface cannot currently be returned, the agent MUST report interface_unavailable. If the available document is malformed, inconsistent with the selected skill or versions, or otherwise fails required validation, the agent MUST report interface_invalid. It MUST NOT accept or return an unvalidated opaque payload as a substitute.¶

10.4. Machine-readable error conditions

This document defines error conditions, but it does not define an error envelope or assign them to concrete A2A protocol elements. The applicable A2A Binding Profile or deployment specification MUST define how a condition is represented and carried, including whether it appears as a protocol error, failed task status, structured message, or another A2A element. These conditions are not skill outputs and are not validated against the selected skill's output_schema.¶

An implementation MUST distinguish at least the following conditions:¶

  • skill_not_advertised: the requested skill_id is not advertised by the selected agent endpoint;¶

  • unsupported_interface_version: the client and agent do not have a mutually supported advertised Skill Interface version;¶

  • interface_unavailable: the selected interface is advertised but cannot currently be returned;¶

  • interface_invalid: a Skill Interface Document is malformed, does not match the preselected skill or versions, fails validation against the selected Skill Interface Schema, or contains an embedded schema that fails digest or schema validation;¶

  • constraint_rejected: a structurally valid requested constraint cannot be honored or enforced by the receiving agent;¶

  • authorization_failed: authentication, authorization, or a required approval check does not permit the requested invocation or side effect; and¶

  • resource_limit_exceeded: processing the interface, schema, input, output, or supporting records would exceed an implementation resource limit.¶

The first two conditions can be detected by a client before it sends describe_skill. A client MUST NOT send the request when the Agent Card does not advertise the selected skill or when no mutually supported interface version exists. If a server receives a request based on stale or inconsistent advertisement information, it MUST report the applicable condition through the selected binding.¶

A client that detects interface_invalid locally MUST reject the document and MUST NOT delegate the domain skill under this framework. An implementation MAY include additional diagnostic details, but those details MUST NOT disclose credentials, sensitive policy state, or information prohibited by local security policy.¶

10.5. Client-agent behavior

The following figure illustrates the conceptual inline flow between a client agent and a remote network management agent. It does not define concrete A2A messages or protocol elements. Inline delivery does not replace Schema References. Each reference retains its stable identity, version, dialect, and digest while carrying the schema content in its resolution field.¶

       Client Agent                         Remote Agent
            |                                    |
            |------ Retrieve Agent Card -------->|
            |<----- Skills and A2A endpoint -----|
            |                                    |
            | Select advertised interface and    |
            | skill versions                     |
            |                                    |
            |--- describe_skill(skill_id) ------>|
            |<-- Skill Interface Document -------|
            |       Schema References:           |
            |       - input schema               |
            |       - output schema              |
            |       - supporting records         |
            |       resolution.type = inline     |
            |       embedded schema content      |
            |                                    |
            | Validate interface structure,      |
            | references, digests, and schemas   |
            |                                    |
            |--- Delegate validated request ---->|
            |<--- Status, output, and records ---|
            | Validate response using cached     |
            | Schema References                  |
¶

The client verifies each embedded schema against the digest declared by its Schema Reference before using it. The following steps define the v1.0 client behavior.¶

A client agent performs the following sequence:¶

  1. retrieve the target Agent Card and obtain its A2A endpoint, agent version, and advertised skill identifiers;¶

  2. verify that both describe_skill and the selected domain skill are advertised, and select an advertised Skill Interface version and domain skill version;¶

  3. call describe_skill for the selected skill_id, without in-band version negotiation, using the selected A2A Binding Profile or deployment mapping;¶

  4. validate the returned Skill Interface Document against a trusted local copy of the selected Skill Interface Schema and verify that its interface_version and skill_version equal the versions selected before the request;¶

  5. verify every embedded domain schema against its Schema Reference digest;¶

  6. validate the outgoing skill input against input_schema;¶

  7. delegate the task through the Agent-to-Agent protocol using that mapping;¶

  8. receive task status, typed skill output, and supporting records according to that mapping;¶

  9. validate the skill output against output_schema and validate the supporting records; and¶

  10. preserve, forward, display, or interpret them according to local policy.¶

Before delegating a domain skill under this framework, the client agent MUST possess a successfully validated Skill Interface Document obtained from that target's describe_skill skill. If describe_skill is absent, fails, returns a document for a different skill or version, or returns a document that cannot be validated, the client agent MUST NOT delegate the domain request using the procedure defined in this document.¶

The client agent MAY reuse a cached Skill Interface Document without calling describe_skill before every task when the cache entry is bound to the same target identity, agent version, skill identifier, skill version, and, when advertised, interface-document digest. A change to any of those values invalidates the entry and requires a new describe_skill exchange before the next delegation.¶

A generic client agent can validate and route an unfamiliar vendor schema without understanding its domain semantics. A domain-aware orchestrator may install optional handlers keyed by stable schema URI to evaluate operational thresholds, incident records, configuration policy, or other domain behavior.¶

json { "resource_id": "network-resource-123", "condition": { "metric": "utilization", "operator": "gte", "threshold": 80, "unit": "percent" } } ¶

The receiving agent validates the same input, performs the evaluation, and produces this domain output:¶

10.7. Composition of consecutive skills

When the output of one skill becomes the input to another skill, the component initiating the downstream delegation is the client agent for that interaction. That component may be a centralized orchestrator or the upstream agent itself communicating directly with the downstream agent. The same composition rules apply in either topology.¶

The downstream delegation creates a new Agent-to-Agent task with its own task identifier. The delegating component MUST retain the upstream and downstream task identifiers as distinct values. It SHOULD preserve a correlation mapping that includes the relevant agent identities or endpoints, skill identifiers, task identifiers, and timestamps for observability, audit, and troubleshooting. An A2A Binding Profile or deployment specification SHOULD define how this cross-hop correlation metadata is carried or recorded. Fields such as workflow_id, step_id, attempt_id, and parent_a2a_task_id may be used when defined by the applicable domain schema or binding, but they do not replace protocol task identifiers.¶

The following figure shows the reference comparison and validation decisions performed by that delegating component.¶

 Upstream Agent                 Delegating Component
       |                                  |
       |-- Output payload ---------------->|
       |   output_schema reference        |
       |                                  |
       |                         Retrieve downstream
       |                         Skill Interface
       |                                  |
       |                                  v
       |                         Downstream input_schema
       |                              reference
       |                                  |
       |                    Compare URI, version,
       |                    dialect, and digest
       |                                  |
       |                +-----------------+----------------+
       |                |                                  |
       |              Match                         No exact match
       |                |                                  |
       |      Validate output against              Reject direct
       |      downstream input schema               composition
       |                |
       |                v
       |      Create new downstream A2A task
       |      and delegate validated input
       |                |
       |                v
       |        Downstream Agent
       |      validates and processes
¶

The standardized Schema Reference allows an orchestrating system or delegating agent to determine direct-composition eligibility without interpreting a domain-specific schema. Direct composition MUST require the Schema Reference for the transferred upstream output payload and the Schema Reference accepted for the corresponding downstream input to have the same schema_uri, version, dialect, and digest. Because version 1.0 carries schemas inline, the delegating component also verifies that each embedded schema matches its declared digest.¶

This exact-match rule is intentionally conservative. Two schemas can be structurally similar, or can both accept a particular instance, while assigning different meanings, units, defaults, constraints, or operational consequences to the same fields. Inferring compatibility from shape or successful validation alone could therefore connect semantically divergent interfaces. Comparing the complete portable identity and content digest gives v1.0 a deterministic composition decision without requiring domain interpretation, schema negotiation, or a standardized compatibility algorithm. The rule does not assert that only identical schemas can ever interoperate; it limits what this specification treats as direct composition.¶

The orchestrating system or delegating agent MUST validate the transferred instance mechanically against the downstream input schema before delegation, and the receiving agent MUST validate the received instance before processing it. Neither operation requires the orchestrating system or delegating agent to understand the schema's domain semantics.¶

If those Schema Reference fields do not match, the delegating component MUST NOT perform direct composition under this specification.¶

An implementation can use an out-of-band transformation mechanism before delegation. Transformation discovery, trust, execution, and provenance are outside the scope of this document. Any resulting payload enters this procedure as a new input and is subject to ordinary input validation against the downstream input_schema.¶

Matching Schema References and successful instance validation establish structural compatibility, not operational correctness. The receiving agent remains responsible for domain-semantic validation, authorization, policy evaluation, and operational safety before acting on the input.¶

11. Schema Publication and Packaging

11.1. Vendor release artifacts

Agent domain schemas are deployment-independent source artifacts. The standardized Skill Interface Schema is a separately versioned common artifact; an implementation packages an exact trusted copy rather than maintaining an agent-specific variation. A vendor release pipeline SHOULD:¶

  1. validate all schemas;¶

  2. test representative inputs and outputs against them;¶

  3. assign stable schema URIs and versions;¶

  4. compute schema digests;¶

  5. when publishing a schema bundle, produce a bundle manifest; and¶

  6. sign or otherwise integrity-protect any published schema bundle.¶

Producing a schema bundle is optional. A bundle, registry, or agent package may provide deployment-local source material for assembling a Skill Interface Document. Regardless of that source, the resulting v1.0 document contains the domain schemas inline. The release pipeline does not need access to a customer registry.¶

11.2. Agent initialization

Before advertising schema-interface support, an agent SHOULD:¶

  1. load and integrity-check its packaged Skill Interface Schema;¶

  2. load its domain input, output, and supporting-record schemas;¶

  3. assemble a Skill Interface Document for each advertised skill version;¶

  4. validate each document and each inline schema digest; and¶

  5. retain an immutable validated representation for describe_skill.¶

Failure to load, assemble, or validate an interface prevents that skill version from being advertised through this framework. An implementation MUST NOT silently fall back to an opaque unconstrained payload.¶

12. Deployment-local Schema Management

Version 1.0 defines inline schema delivery on the wire. This section describes optional deployment-local mechanisms for storing, governing, distributing, and preparing schemas before an agent returns a Skill Interface Document. These mechanisms do not change the v1.0 Schema Reference and do not require a client agent to retrieve schema content from an additional endpoint.¶

12.1. Trusted cache

A client agent MAY cache a validated Skill Interface Document, its verified inline schemas, and compiled validators. Cache reuse is governed by the requirements in Section 10.5. An agent MAY also cache schemas obtained from its deployment-local management system before assembling its immutable interface documents.¶

12.2. Optional schema registry

A registry may provide centralized storage, subject versioning, references, compatibility checks, publisher metadata, and governance. [CONFLUENT] is one non-normative example of this class of service. This document does not require a particular registry implementation or REST API.¶

When a registry is used, the agent publisher or deployment maps registry-local subjects, versions, and identifiers to stable schema URIs and digests while assembling the Skill Interface Document. The v1.0 document still carries the selected schema content inline and does not expose registry connection information to the client agent.¶

12.3. Offline bundle

An air-gapped deployment MAY install an approved schema bundle with the agent package. The agent uses that bundle to assemble and validate its Skill Interface Documents and then returns their schemas inline. A bundle may also distribute the standardized Skill Interface Schema to client implementations, but it does not replace inline delivery of a remote skill's domain schemas.¶

13. Schema Evolution and Compatibility

Schema publishers MUST treat a published schema version and digest as immutable. A changed schema receives a new version and digest.¶

Compatibility policy SHOULD be applied to a governed schema family. Structural compatibility checking is necessary but not sufficient. It cannot establish that units, operational interpretation, authority, or supporting-record quality remain compatible.¶

A breaking semantic change requires a new major version even if a structural JSON Schema checker accepts the change. Examples include:¶

  • changing a utilization value from percent to a fraction;¶

  • changing a timestamp from observation time to processing time;¶

  • changing a supporting-record classification from authoritative to inferred; or¶

  • changing a configuration artifact from candidate to applied state.¶

The Skill Interface Document MUST identify the exact schema versions currently used by the skill. When a registry is used as a deployment-local management mechanism, the document assembler MUST select an exact version and digest; it MUST NOT substitute a mutable latest value. A client validates and uses the schema embedded in the accepted document.¶

14. Security Considerations

14.1. Schema trust

A syntactically valid schema is not necessarily trustworthy. A client agent applies policy for trusted publishers, schema identities, digests, versions, and dialects.¶

14.2. Arbitrary retrieval

Following arbitrary schema URLs can expose a client agent to server-side request forgery, credential leakage, malicious redirects, and availability attacks. Version 1.0 Schema References contain inline schema content and MUST NOT direct the client agent to retrieve a schema from an arbitrary URL. Deployment-local schema-management tools that contact registries or other services remain subject to administrator-configured trust and network policy.¶

14.3. Resource limits

An implementation MUST enforce limits on schema size, nesting, reference depth, reference cycles, compilation time, payload size, and cache consumption. When an operation is rejected because one of these limits would be exceeded, the implementation MUST report the resource_limit_exceeded machine-readable condition defined in Section 10.4 through the applicable binding. The error response need not disclose the configured threshold or other sensitive implementation details.¶

Version 1.0 does not define numeric interoperability minima for these limits. An A2A Binding Profile or deployment specification MAY define minimum supported capacities or maximum interoperable sizes for implementations that claim conformance to that profile or specification.¶

14.4. Schema validation and authorization

Schema validation establishes structural conformance, not caller authority, operational safety, truth, or permission to modify a network. The authority member of a Skill Interface Document is descriptive and MUST NOT be interpreted as a permission grant or evidence that an approval has been obtained.¶

At invocation time, the receiving agent or hosting platform MUST authenticate the caller and authorize the requested skill, resources, operation, and applicable constraints under current local policy. It MUST repeat or refresh the authorization decision when required by that policy before causing a side effect. A cached Skill Interface Document, successful schema validation, or a previous authorization decision MUST NOT substitute for a required current decision. A denied authentication, authorization, or required approval check MUST reject the invocation with the authorization_failed machine-readable condition defined in Section 10.4.¶

This document does not mandate an authorization model. Deployments may use RBAC, ABAC, capability-based authorization, external policy decision points, human or automated approval workflows, or another model that satisfies these runtime requirements.¶

14.5. Supporting-record integrity and provenance

Supporting records can be stale, replayed, forged, selectively omitted, or derived from untrusted inputs. A supporting-record schema SHOULD require the source, producer, relevant observation and production times, integrity data, derivation, and classification needed by its domain. Deployments define freshness and retention policy appropriate to the operation.¶

14.6. Injection

Text, CLI configuration, tool output, model output, and supporting-record payloads are untrusted data. An agent does not treat instructions embedded in those artifacts as authorized task instructions unless the applicable schema and policy explicitly assign them that role.¶

14.7. Interface integrity and substitution

The remote agent and client agent MUST integrity-check the packaged Skill Interface Schema before using it. A local implementation MUST NOT modify the standardized schema while adding domain schemas.¶

A client agent verifies that a retrieved Skill Interface Document identifies the requested agent skill and advertised skill version. It validates the document against the selected Skill Interface Schema and verifies all embedded schema digests. A structurally valid document for a different skill or version MUST NOT be accepted as a substitute.¶

15. Operational Considerations

Interface retrieval and validation SHOULD NOT add a describe_skill exchange to every task. A client agent caches validated Skill Interface Documents, verified inline domain schemas, and compiled validators. A cache entry is bound to the agent identity, skill identifier, skill version, interface version, and, when advertised, interface-document digest. A changed advertised version or digest invalidates the corresponding entry.¶

An implementation SHOULD expose diagnostics identifying:¶

  • the Skill Interface Schema version and skill version selected;¶

  • schema URIs, versions, and digests used;¶

  • inline-schema digest verification results;¶

  • validation failures;¶

  • missing, malformed, or untrusted schemas; and¶

  • compatibility or policy failures; and¶

  • upstream-to-downstream task mappings, qualified by agent identity or endpoint.¶

Deployments using a registry or another management service SHOULD test that a running agent can continue serving previously assembled and validated Skill Interface Documents during temporary management-service unavailability. They SHOULD also define cache refresh and schema-revocation behavior.¶

16. IANA Considerations

This early version does not request any IANA actions. A later version may request identifiers for Skill Interface versions, media types, or URN namespaces after the representation and protocol mapping stabilize.¶

17. Open Issues

The following issues require further review:¶

  1. possible future in-band version-negotiation behavior when multiple interface versions are supported;¶

  2. representation of confidential supporting records and access-controlled artifact references;¶

  3. schema revocation and emergency withdrawal;¶

  4. signature format for schema bundles and Skill Interface Documents;¶

  5. a possible future interface version supporting non-inline schema delivery without making a registry API normative; and¶

  6. a reusable A2A Binding Profile for describe_skill, skill input, skill output, and supporting records.¶
